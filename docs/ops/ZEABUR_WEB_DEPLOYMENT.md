## 2. 故障原因与处理过程

| 问题                     | 证据与原因                                                                                                                      | 本次处理                                                      | 下次预防                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 发布版本与需求不一致     | 官方镜像标签不能证明它等于本地 `main`；最初的镜像切换没有满足指定提交的发布要求                                                 | 改为从固定提交打包源码                                        | 开始前记录目标服务、提交 SHA、版本及镜像目标；发布后检查实际容器版本                               |
| 没有 GitHub Actions 运行 | 仓库级 Actions 开关与工作流本身均停用；仅启用工作流或推送分支没有产生运行                                                       | 恢复原设置，使用源码上传                                      | 在提交构建前查清仓库开关、工作流开关与触发条件；不得用临时空提交反复试探                           |
| 构建脚本缺失             | 共享 `zeaburctl.py` 的 `archive_project()` 按目录名递归排除 `build`，误删了 `scripts/build`；它与 Docker 的忽略匹配语义不同     | 改用完整 ZIP，保留构建脚本                                    | 用 Docker 自身的 `.dockerignore` 规则导出上下文；检查 ZIP 内关键文件，避免再次调用旧打包器重新打包 |
| `fumadocs-mdx` 无法导入  | 运行环境的 `NODE_ENV=production` 被注入构建步骤，原 `npm ci` 未明确包含开发依赖；该依赖位于 `devDependencies`，但生产编译需要它 | 构建阶段显式使用 `npm ci --include=dev --include=optional`    | 将构建依赖和运行依赖分开；构建阶段始终包含开发依赖                                                 |
| 环境模块缺失             | 原 ZIP 中存在 `src/lib/env/runtimeEnv.ts`，上传后的编译却无法解析它                                                             | 用普通路径的 tar 文件携带源文件，执行 `COPY` 后、编译前还原   | 自动保护应用源码中的 `env` 目录，并在云端执行文件存在检查                                          |
| 隐藏路由遗漏             | 上传链路遗漏 `.well-known` 目录，导致 A2A 路由解析警告；只看到“带警告编译成功”不足以证明应用完整                                | 同样还原两个 `.well-known` 路由                               | 同时保护应用源码中的隐藏目录；发布后逐个访问发现接口                                               |
| Chromium 下载慢且重试    | 浏览器与 FFmpeg 下载多次发生 30 秒连接超时，延长构建                                                                            | 从固定摘要的官方 Web 镜像复用匹配的浏览器文件，安装所需系统库 | 检查 Playwright 版本、浏览器修订号和实际启动；版本变更时更新经过验证的浏览器基线                   |
| 提交超时与重复构建       | 提交接口返回 `502/504` 后，后台数分钟后仍创建任务；过早重试会产生新任务，并取消上一轮构建                                       | 等待后台任务出现，按上传 ID 与部署 ID 核对                    | 超时后先查询同一请求对应的任务；只有确认未创建任务或任务已终止，才考虑再次提交                     |
| 状态判断过早             | 一轮任务曾显示 `FAILED`，随后又变成 `BUILDING`，最终时间为空；日志止于发送 tarball，之后被新发布取消                            | 最终以完成时间、实际镜像和运行检查验收                        | 观察超时、一次读失败、瞬时状态均不等于终止；不要仅凭固定等待时长取消任务                           |

**尚未证明的原因：**没有权威证据确认 Zeabur 存在硬性的“30 分钟构建上限”，
也未取得那轮 tarball 传输停滞的明确平台错误。不要把这个猜测写成平台限制或据此重启构建。
源码中的 `env`/隐藏目录遗漏、浏览器网络重试则有打包内容与构建日志的直接证据。

## 3. 复部署的选择顺序

### 优先：构建并验收不可变的 Web 镜像

已有 [GHCR Web 工作流](../../.github/workflows/ghcr-runner-web.yml) 和
[镜像验收脚本](../../scripts/ci/verify-runner-web-image.mjs)。工作流构建 `runner-web`、
`linux/amd64`，使用提交 SHA 作为镜像标签，验证完成后才推送。
详见 [Docker 指南](../guides/DOCKER_GUIDE.md)。

两次源码发布均未依赖 GitHub Actions，自动部署未在本任务中开启。
下一次必须先核实仓库及工作流的实际状态。
启用仓库级 Actions 曾被自动审批拒绝，因为这扩大了本次发布以外的安全治理变更范围；
不要绕过拒绝去启用所有工作流。需要改变该设置时，先明确具体工作流和权限范围。

发布应绑定经过验证的镜像摘要或提交标签。不要用浮动 `latest` 证明某个 `main` 提交已部署。

### 回退：准备固定提交的源码包

已将成功路径固化为
[发布包准备脚本](../../scripts/ops/prepare-zeabur-web.py) 和
[浏览器基线](../../config/deploy/zeabur-web.json)。脚本需要 Python 3.12+、Git、Docker CLI
及可用的 Docker daemon。

```bash
python3 scripts/ops/prepare-zeabur-web.py \
  --ref 2e747990284fdab59619fdbd6e41f492322511c0 \
  --output /private/tmp/omniroute-zeabur-next
```

每次使用新的输出目录。脚本只从已提交的 Git 引用取源码，工作区中未提交的修改不会进入发布包。
`--ref` 必须显式指定。上例固定的是本次翻译修复提交，后续应替换为当次审阅过的提交 SHA。
重试提交时，修复尚在独立工作分支，旧 `main` 仍缺少修复；随后再将修复与本文合入 `main`。
后续使用主分支前，先同步远程，并确认它包含修复提交：

```bash
git fetch origin main
git merge-base --is-ancestor 2e747990284fdab59619fdbd6e41f492322511c0 origin/main
```

退出码为 `0` 才证明远程主分支包含该修复。打包时仍应明确指定当次审阅过的提交 SHA。
它会：

1. 解析并固定提交 SHA；输出目录必须位于仓库外，且尚不存在。
2. 使用 Docker 的真实忽略规则导出构建上下文，保留 `scripts/build`。
3. 检查关键构建文件，拒绝本地环境文件、依赖目录和根目录私有路径。
4. 检查锁文件中的 Playwright/Playwright Core 是否匹配已验证的浏览器基线。
5. 自动生成需要还原的 `env`/隐藏应用源码清单与 tar 文件。
6. 生成包含开发依赖安装、源码还原和 Web 最终阶段的 Dockerfile。
7. 在生成的镜像构建末尾，以 `node` 用户实际启动 Chromium，检查修订号与版本。
8. 输出 `source.zip`、可审阅的 `Dockerfile` 和 `release-manifest.json`；
   清单包含提交、版本、ZIP SHA-256、还原路径和源码文件 SHA-256。

脚本执行的是发布包准备，**上传与线上切换是后续操作**。
2026-10-11 重试已在真实云端构建中执行生成的 Dockerfile，并通过末尾浏览器启动检查。
后续版本仍需重新执行完整镜像构建与运行验收；打包成功本身不等于构建成功。

浏览器基线中的旧应用版本只是浏览器文件来源，不是将要发布的应用版本。
升级 Playwright 后，脚本会拒绝复用旧基线；先验证新的浏览器镜像，更新版本、修订号、
浏览器版本及镜像摘要，然后重新打包。不能为了让检查通过而只修改版本字符串。

## 4. 上传、等待与恢复

由 `zeabur-ops` 使用用户共享的 `zb` 工具读取已有凭据及目标映射。
状态检查的已验证命令：

```bash
/opt/homebrew/opt/python@3.14/bin/python3.14 \
  /Users/andyliu/Developer/work/zeaburcli/zeaburctl.py status OmniRoute
```

上传准备好的 ZIP 时，沿用本次成功的 API 顺序；参考
[Zeabur Public API](https://zeabur.com/docs/en-US/developer/public-api)：

1. 对 **现有 ZIP 的原始字节**计算 SHA-256，并按 API 格式 Base64 编码。
2. 请求 `/v2/upload`，取得预签名地址和 `upload_id`。
3. 将同一 ZIP 上传到预签名地址；该请求不携带 Zeabur API 密钥。
4. 对该 `upload_id` 调用 `/v2/upload/{upload_id}/prepare`，指定现有服务与环境。
5. 记录提交时间、上传 ID、部署 ID，后续只跟踪同一任务。

这些步骤现由 [单次上传与状态查询脚本](../../scripts/ops/submit-zeabur-web.py) 执行。
脚本读取共享工具已有凭据与服务映射，校验 ZIP 与发布清单一致，直接上传原 ZIP。
执行 `submit` 代表发布操作，必须已有明确发布授权；`status` 只读取已有任务。

```bash
python3 scripts/ops/submit-zeabur-web.py submit \
  --alias OmniRoute --package-dir /private/tmp/omniroute-zeabur-next
python3 scripts/ops/submit-zeabur-web.py status \
  --alias OmniRoute --package-dir /private/tmp/omniroute-zeabur-next --logs 8 --runtime-summary
```

`submission.json` 在第一次网络提交前创建，并逐步保存上传 ID、服务、环境和旧部署 ID。
已有该文件时，脚本拒绝再次 `submit`，包括第一次操作超时的情况。
提交未确认时退出码为 `2`，不代表任务已失败；随后运行 `status`，按 `uploadID`
匹配后台任务，不把列表最新条目直接认作这次发布。等待状态未匹配到任务时继续观察。
若上传 ID 尚未取得，先核查目标和已创建任务；不要删除记录来绕过重复提交保护。
脚本不自动重试任何发布请求，不输出预签名地址、API 密钥或上游错误正文。
本次 API 返回的构建日志为时间倒序，单次返回了 500 条；不能直接取数组末尾来判断最新进度。
`status --logs 8` 先按时间排序再选最新日志，并移除 URL 查询参数及 Bearer 认证值。
运行日志也要核对部署和日期：重试中不指定部署 ID 的旧查询返回了上一轮的停止日志，
不能据此判断新实例故障。`--runtime-summary` 明确按本次部署 ID 查询，过滤早于
`startedAt`（缺失时使用 `createdAt`）或没有有效时间的记录，只输出时间范围与条数。
它不输出运行日志正文，也不把日志窗口当作健康或模型对话成功的证据。

不要把准备好的目录再次交给旧 `archive_project()`，否则其按名称排除规则会重新造成源码缺失。
不要打印凭据、Cookie、预签名地址或加密密钥。

如果提交返回网关超时：先检查部署列表，核对 `uploadID`；本次数次请求在数分钟后才出现任务。
不要立即重复提交。观察等待超时也不意味着后台进程已停止。
如果状态查询暂时失败，重新查询同一任务；检查 `finishedAt`、最后日志时间和实际镜像，
确认任务终止后再决定是否重新发布。构建器初始化阶段本次多次耗时约十分钟，但这不是保证或固定 SLA。

额度恢复后的诊断同样先读取现有任务：若它已完成，就进入运行验收；
若仍活跃，就继续跟踪；不能因会话暂停而重新启动部署。

## 5. 发布前后验收与回滚

### 发布前

- 确认服务、环境、Git 提交、应用版本和镜像目标。Gemini Web 使用包含 Chromium 的 Web 运行时。
- 记录旧的实际镜像引用及摘要；保留可用的回滚版本。
- 备份持久化 SQLite 数据，核对数据卷与 `DATA_DIR`；加密凭据所需密钥保持可用。
- 审阅发布清单、Dockerfile、关键源文件及浏览器基线。

### 发布后

1. 服务与对应部署均为 `RUNNING`，实际镜像对应这次发布。
2. 在容器内读取应用版本；对于镜像发布，还核对提交标签/镜像 revision。
3. `/api/health` 和 `/api/health/ping` 均返回 HTTP `200`；后者实际调用数据库检查。
4. 两个 `.well-known` 发现接口均返回正确版本，登录页可访问。
   在中文界面打开 `/home`，确认快速入门、提供者拓扑、最近请求显示译文，
   不出现 `home.quickStart` 等原始翻译键。
5. 在运行容器内无头启动 Chromium，并关闭测试浏览器。
6. 用新建、无账号 Cookie 的浏览器上下文检查 Gemini 公共页面访问。
7. 另行使用有效账号 Cookie 做一次真实模型请求，验证账号、额度及模型权限。
   这一步才证明登录后的 Gemini Web 推理链路可用。
8. 确认数据库与备份状态。不要只根据“构建成功”结束验收。

### 回滚

健康或数据库检查失败时，切回发布前记录的实际镜像，再执行相同运行验收。
数据库恢复需要先核对迁移兼容性，不能盲目用旧镜像读取已迁移的数据。
首次切换前的镜像是官方 `3.8.51-web`；以后以各次发布前记录为准。
2026-10-11 翻译修复重试前，回滚基线已是上一轮实际构建的 `3.8.52`：
`registry-oci.zeabur.cloud/e-6a957b21e9580d2806c946ca/s-6a9c26e973ae037aa4de36e8:d-6aca4d48da7cf920c2637301`。

关键回归检查：


测试覆盖嵌套 `build` 目录与隐藏/环境模块的打包保真、还原文件字节一致性、
旧浏览器基线拒绝新 Playwright、还原步骤位于编译之前、已有输出目录的数据保护，
以及显式指定源码提交、提交超时后保留上传 ID、重复提交保护、目标核对、
ZIP 篡改拒绝、日志排序及运行日志年龄过滤。
发布工具和平台行为变化时，先更新这些检查与实测记录，再调整流程。

合入主分支前，另按项目要求执行 `npm run test:unit` 和 `npm run test:vitest`。
本次本地合并验收发现复用的 `node_modules` 与锁文件不一致，包括缺失
`@agentclientprotocol/sdk`，因此先在独立工作目录执行
`npm ci --include=dev --include=optional`，再使用符合依赖要求的 Node `24.19.0` 验证。
不要把旧依赖缓存引起的失败认作源码回归，也不要在共享工作目录重装其他会话的依赖。
部分单元测试要监听 `127.0.0.1`；受限沙箱返回 `EPERM` 时，监听等待可能一直不结束。
先用最小监听检查确认权限原因，再在允许本地监听的环境运行；不通过删除测试绕过检查。
macOS 还存在 `/var` 与 `/private/var` 的真实路径别名，导致三个路径断言失败；
将测试临时目录设为 `TMPDIR=/private/tmp` 后，这三个用例均通过。
同一聚焦检查共 31 项，通过 30 项；剩余日志孤儿清理用例预期清理 5 个文件，实测为 3 个。
该用例及实现与此次合并前远程 `main` 一致，本次修复未触及它们。
这一既有失败尚未解决，不能把完整单元测试记为通过；是否带已知失败合并需明确记录决定。
