# 界面翻译加载与中文遗漏审计

## 范围与结论

本次检查以已发布的 `main` 提交 `918d4f301947e8edde50700152a42e7bcded5241` 为基线，
在 `codex/zeabur-deployment-runbook` 中检查并修复。修复提交
`2e747990284fdab59619fdbd6e41f492322511c0` 已于 2026-10-11 发布到 Zeabur
`omniroute-official`，部署 ID 为 `6acaec01c0a5252069b839fb`，服务与部署均为 `RUNNING`。
此次部署先使用独立分支的固定提交，随后再将修复与部署文档合入 `main`。
后续发布应先同步远程，并确认所选提交包含 `2e74799028` 的修复。

- 扫描 **160 个页面与错误、加载等路由边界**及 **1,951 个关联模块**。
- 检查页面实际继承的翻译集合、客户端组件引用、字面翻译键及服务端翻译调用。
- 检查 **67 个界面语言目录**，每个目录的键集合与英文的 **13,744 个键**一致。
- **920,848 条文本**全部通过 ICU 编译检查，没有缺键或 `__MISSING__:` 占位文本。
- 全局错误页另使用独立的小型翻译目录；已检查其与完整目录同步及英文回退。
- 补上首页布局后，扫描未发现其他可静态确认的翻译集合遗漏或缺失字面键。

键完整和语法有效不代表译文质量完整。本次人工核对了中文与英文相同的文本，
发现一批真实的英文提示遗漏，已经修订。其他语言没有逐条进行人工语义审校。

## 确认的问题与修复

| 问题                                | 原因                                                          | 修复及验证                                                                                       |
| ----------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `/home` 显示 `home.quickStart` 等键 | 首页迁出 `/dashboard` 后没有自己的翻译布局                    | 增加首页布局，生成器覆盖新路径，检查中英文首页键及布局接入                                       |
| 旧 MITM 路由错误页固定显示英文      | 文本直接写在组件中，没有调用翻译                              | 复用 `mitm`、`settings`、`common` 现有译文；补齐系统路由集合；实际渲染中英文组件，确认无翻译错误 |
| 简体、繁体中文部分功能提示仍为英文  | 对应键已经存在，所以覆盖率检查通过，但值与英文相同            | 两种中文各修订 69 项文本；检查中文内容、参数插值、文件名示例及额外费用提醒                       |
| 全局错误页可能退回错误语言          | 错误页直接匹配 Cookie，未使用正常页面支持的别名和大小写规范化 | 使用同一 `resolveRequestedLocale()`；回归检查禁止重新使用旧匹配方式                              |

中文修订涉及 Codex 本地冷却和付费额度、单模型并发限制、代理订阅配置和重载错误、
额度池可用时段、请求时间线及地址标签。少量已有中文的地址标签同时统一了用语。
没有更改收费策略、额度逻辑或账号状态。

检查后，排除既有“不需要翻译”清单的统计仍有 **128 项简体中文**、**137 项繁体中文**
与英文相同，主要为产品名、技术缩写、地址示例和符号。
该指标分别为 `0.9%`、`1.0%`，均在现有质量基线之内；不能将其解释为页面缺键数。

## 持续检查

新增 [路由翻译审计工具](../../scripts/i18n/audit-route-messages.mjs)，使用 TypeScript AST
识别翻译调用，跟踪静态与字面动态导入，并检查实际祖先布局。
它包含钩子别名、类型断言、多行参数和根级富文本调用的回归样例。

```bash
npm run i18n:check-routes
# 完整报告含动态键调用的位置
npm run i18n:check-routes -- --json

node scripts/i18n/check-key-completeness.mjs
npm run check:ui-icu
npm run i18n:check-ratio -- --locale=zh-CN,zh-TW
```

新的 [审计回归检查](../../tests/unit/i18n-route-audit.test.ts) 会随单元测试执行，
能复现“路由迁移后缺布局”和“组件引用不存在的键”。
[中文文本检查](../../tests/unit/i18n-zh-ui-audit.test.ts) 会防止本次修订回退为英文，
同时保留参数和费用提醒。全局错误页检查位于
[global-error-messages.test.ts](../../tests/unit/global-error-messages.test.ts)。

## 验证边界与发布验收

扫描还记录了 **310 个动态键调用或探测**，例如按任务状态、菜单配置或接口数据选择键。
静态检查能证明其命名空间已加载，但不能枚举所有运行时输入，也不能证明每个分支的
富文本处理、接口错误状态和浏览器交互都已执行。
检测器只解析静态和字面动态导入，不代替浏览器测试。

三种语言的首页均显示快速入门、提供者拓扑、最近请求和完整文档的对应译文。
发布前首页有 110 条国际化错误、可见内容显示 `home.quickStart` 等键；发布后均未发现。
只搜索响应 HTML 内的中文会产生假阳性，因为响应含有尚未应用到界面的翻译数据。
健康检查与 HTML 字符串匹配都不足以替代实际页面验收。

后续修改相关交互时仍应做针对性浏览器检查。
